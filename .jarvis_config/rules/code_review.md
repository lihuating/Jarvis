# 代码审查规则

## 规则简介

本规则定义了代码审查的标准流程、检查清单和注意事项。在编写或修改代码后，应自动触发代码审查流程，确保代码质量、安全性和可维护性。

## 触发条件

- 编写或修改代码后
- 用户明确要求进行代码审查时
- Git 提交前（配合 `jgc` 使用）
- Pull Request / Merge Request 审查时

## 你必须遵守的原则

### 1. 审查启动流程

**要求说明：**

- **必须**：审查启动时先运行 `git diff` 或 `git diff --stat` 查看变更范围
- **必须**：识别文件类型（代码文件、配置文件、基础设施文件），对不同类型应用不同审查策略
- **必须**：对配置文件变更施加更严格的审查
- **禁止**：跳过变更分析直接给出审查结论

### 2. 配置变更审查（关键重点）

**要求说明：**

- **必须**：对配置文件中的任何数值变更追问原因 — 为什么是这个值？依据是什么？
- **必须**：要求数值变更需有测试证据支撑
- **必须**：检查数值是否在推荐范围内
- **必须**：评估数值达到限制时的影响
- **禁止**：对配置文件中的魔术数字视而不见

### 3. 代码实现审查清单

#### 3.1 日志打印
- 检查日志打印级别是否正确
- 检查日志参数是否完整打印
- 检查异常是否正确打印
- 避免过多或无用的日志打印

#### 3.2 异常处理
- 异常该抛出时必须抛出，不能吞掉
- 使用规范的异常编码
- 函数失败错误码必须正确处理，不能统一按一种情况处理

#### 3.3 业务逻辑
- 逻辑是否正确
- 场景是否遗漏

#### 3.4 并发访问
- 并发访问覆盖是否全面
- 是否存在竞态条件
- 是否有有效的逻辑流程分析

#### 3.5 复位码
- 涉及新增或变更复位码时，确保与现有复位码不重复

#### 3.6 锁粒度
- 锁粒度是否合理
- 高性能模块中锁是否限制随意调用
- 维测等优先级任务不能调用内存分配锁导致影响业务

#### 3.7 临界区分析
- 评估加锁临界区内是否存在调用外部函数
- 评估外部函数中再次获取本锁的概率与风险

#### 3.8 性能优化
- 是否使用缓存
- IO 是否异步处理
- 日志是否使用缓存
- 高频调用模块是否有缓存性能考虑

#### 3.9 资源消耗
- 关注内存或 CPU 增加情况（内存、CPU、mmap 等资源消耗）
- 结构体增加字段需关注内存增加
- 考虑是否需要输出 RN 文档
- **资源消耗规范**：每个进程每个 build（一周）对内不超过 4M，对外不超过 5M；单个进程超过 4M 平台测试会提单；不同进程中同样原因导致的增长总计超过 4M 也会提单

#### 3.10 容器权限
- 容器间共享目录的权限问题
- 能力（capability）问题
- 是否存在无权限的情况

#### 3.11 模块耦合
- 是否涉及与其他非 OSS 守护模块的耦合代码合入
- 涉及则需要进行合入策略检查

### 4. 代码规范审查清单

#### 4.1 代码去重
- 同一段代码在超过 3 个地方使用时，需封装函数

#### 4.2 命名规范
- 检查命名拼写是否正确
- 命名与实际含义是否相符
- 用词是否准确
- 是否使用了魔术字
- 是否使用了非公认的缩写

#### 4.3 注释规范
- 函数是否有说明注释
- 对于有入参和返回值的函数，注释是否解释了参数和返回值含义
- 注释是否准确

#### 4.4 资源管理
- 指针是否正确释放
- 文件句柄是否成对使用（open/close）
- 资源在某些场景未释放会导致泄露

#### 4.5 参数规范
- 入参有效性是否检查
- 参数数目是否过多
- 传参为结构体时是否使用指针
- 空指针问题

#### 4.6 安全缺陷
- 是否使用了不安全的加密算法
- 是否硬编码了密码、秘钥
- 密码是否记录到日志
- 未校验的外部输入是否拼接成命令执行（system、popen、exec、eval）
- 是否使用了安全函数

#### 4.7 其他规范
- 代码风格是否与应用整体一致
- 圈复杂度是否大于 8
- 嵌套是否过多
- 分层是否合理，是否存在跨层调用
- 文件夹权限默认 750，文件默认 640
- 代码是否涉及并发编译（相同文件在并行编译中被生成或修改会导致失败）
- 是否使用了不可重入函数
- 开源组件是否按项目要求入项评审后使用

### 5. 审查报告格式

**要求说明：**

- **必须**：按以下结构输出审查报告
- **禁止**：只列出问题不给出改进建议

审查报告格式：

```markdown
## 代码审查报告

### 概要
[变更简要概述]

### 优点
- [代码中的积极方面]

### 问题与建议

#### 严重问题（必须修复）
- [必须修复的问题]

#### 主要问题（应该修复）
- [应该修复的问题]

#### 次要问题（建议改进）
- [建议性的改进]

### 总体评价
[通过 / 有条件通过 / 需要修改]
```

### 6. 审查态度

- **建设性**：聚焦于改进代码，而非批评
- **具体**：指出确切的行号或代码段
- **解释原因**：为建议提供理由
- **区分优先级**：标记严重 vs 建议性
- **肯定好的代码**：对写得好的代码也要指出

## 最佳实践

1. 始终在完整代码库上下文中审查
2. 考虑对现有功能的影响
3. 检查是否有破坏性变更
4. 验证向后兼容性
5. 确保没有引入回归问题
6. 关注修复根本问题，而不仅仅是症状
7. 始终优先考虑防止生产环境故障
